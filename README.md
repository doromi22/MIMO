# MIMO

漫画の講評（フィードバック）を、見開き表示のまま Web 上で行うためのビューアサービス。

2023年に制作し、ドメインを取得して学内展示で公開運用した。**現在は運用を停止している。**

---

## 背景

美術大学のマンガ学科では、作品を PDF にして教員に送り、講評を受ける運用が一般的だった。
しかし漫画は見開きを前提に構成されているため、PDF をスクロールで縦に読むと
意図した読み方にならない。

さらに、表紙の有無によって左右のページが1ページぶんずれるため、
本来「見開き」として組まれたページが分断されてしまう。

この 2 点を解消するために制作した。

なお制作者自身はイラストを中心に描いており、漫画の制作者ではない。
同じ学科で漫画を描いている学生の作業を見て、課題を把握したうえで作った。

---

## 機能

- PDF をアップロードして見開き（2ページ並び）で閲覧
- 「ページをずらす」トグルによる、表紙有無に応じた見開き位置の切り替え
- Socket.io によるリアルタイムコメント
- 公開範囲の設定（全員に公開 / 学生限定 / 先生限定 / 非公開）
- タイトル・タグによる検索、投稿履歴からの公開範囲変更・削除

---

## 技術構成

- Node.js / Express
- MySQL（`mysql2/promise`）
- Socket.io
- pdf-lib（アップロード時のリサイズ・ページ数調整）
- pdf.js（ビューア側の描画。CDN から読み込み）
- EJS
- 認証は bcryptjs + JWT（httpOnly クッキー）

AI コーディングツールは使用しておらず、すべて自分で実装している。

### 動かし方

`.env.example` をコピーして `.env` を作成し、値を設定する。

```bash
npm install --ignore-scripts
node app.js
```

DB は `docs/schema-reconstructed.sql` で作成する。**当時のスキーマ定義はリポジトリに残っていなかった**ため、
これは 2026年に動作確認のためコードから復元したものである（`users` / `comics` / `chat_messages` / `page_status`）。

補足:

- `package.json` の `start` スクリプトは存在しないファイル（`your_app.js`）を指しているため、`npm start` では起動しない（当時のまま残してある）。
- `npm install` に `--ignore-scripts` を付けているのは、実際には使っていない `canvas` がネイティブビルドを必要とするため。

## 表紙オフセットの扱い（実装の経緯）

表紙の有無によるページずれには、**2つの実装が入っている**。

1. **サーバー側でデータを正規化する方式**
   PDF の先頭に白紙ページを挿入し、ページ番号そのものを揃える。
   `addBlankPageToPdf.js` と `POST /add-blank-page`、`page_status` テーブルがこれにあたる。
2. **ビューア側で表示を切り替える方式**
   `showBlankPage` フラグを持ち、描画時に左右どちらに白紙を置くかを分岐する。
   `public/scripts/scripts.js` の `renderPages()` がこれにあたる。

**最終的に動いていたのは 2 の方式**で、1 のエンドポイントはフロントエンドから
呼び出されていない。`/viewer` は `page_status` を読んでテンプレートに渡しているが、
テンプレート側では使われていない。

**確認**: ビューアのトグルを押すと、見開きの組み方が (1,2) から (2,3) に切り替わることを確認した。
一方 `POST /add-blank-page` は画面のどこからも呼ばれておらず、直接叩くと下記の問題4が起きる。

データを入口で揃えれば、ページ番号を扱う箇所すべてに補正が散らばらずに済む。
そう考えて 1 を実装したにもかかわらず、最終的には分岐がビューアに入り、
サーバー側には呼ばれないコードが残った。**避けようとしていた状態そのものになっている。**

## 現在の視点から見た設計上の問題点

制作から時間が経ったあと、自分でコードを読み直して洗い出したもの。
本リポジトリは当時のコードをそのまま公開しており、以下は未修正である。

なお以下の内容は、**2026年にローカルで実際にサーバーを起動して再現を確認している**。
確認にはダミーの PDF（ページ番号と見開き位置の印を入れたもの）と、学生2名・教員1名のアカウント、
公開範囲を変えた作品6件を使った。各項目の「確認」がその結果である。

### 1. 権限判定ロジックがルートごとに重複し、挙動が一致していない

同じ「誰がどの作品を見られるか」という規則が 5 つのルートに、3 通りの実装で存在している。

| 箇所 | 実装 | 自分の非公開作品 |
|---|---|---|
| `/` | インラインの filter（`user_id` 条件あり） | 表示される |
| `/searchform` | インラインの filter（`user_id` 条件なし） | **漏れる** |
| `/search` | インラインの filter（`/searchform` と同一） | **漏れる** |
| `/viewer/:comicId` | `canAccessComic(comic, user, loggedIn)` | 表示される |
| `/comics` | `canAccessComic(comic, req.user)` | — |

`/comics` は第3引数 `loggedIn` を渡していないため `undefined` になり、
「学生限定」「先生限定」の分岐が常に false になる。

**確認**（学生A・学生B・教員で同じデータを見たときの差）:

- 学生Bは、学生限定の作品をトップページでは見られるが、`/comics` では消える。
- 教員は、先生限定の作品が `/comics` から消える（`loggedIn` が渡っていないため）。
- 学生Aは、自分の非公開作品と先生限定作品がトップには出るのに、検索結果には出ない。
- 一方 `/viewer/:comicId` の判定は正しく、公開＝全員 200、学生限定＝学生のみ 200、
  先生限定＝教員のみ 200、非公開＝本人のみ 200 だった。

つまり**画面ごとに答えが違う**状態で、判定そのものが間違っているのではなく、
同じ規則の実装が複数あることが原因だった。

**ドメイン規則を HTTP ハンドラに散らかすとこうなる**という例であり、
現在は規則を一箇所に集める設計を取るようにしている。

### 2. 静的配信と WebSocket が権限判定を迂回している

`/viewer/:comicId` では権限を確認しているが、PDF 本体は
`app.use('/uploads', express.static(uploadDir))` で無条件に配信していた。

つまり公開範囲を 4 段階に分けて設計したにもかかわらず、
**ファイル自体は URL を知っていれば誰でも取得できる状態**だった。

同じことがコメント機能にも当てはまる。Socket.io の `joinRoom` は
`comicId` を受け取ってそのまま参加させており、権限を確認していない。
非公開作品のコメントも、`comicId` さえ分かれば購読・投稿できた。

さらに、未ログインでもコメントが書ける。`authenticateToken` が未ログインのユーザーに
`username: 'guest'` を入れる一方、ビューアのテンプレートは `if (username)` で
コメント欄の表示を決めているため、ゲストにもコメント UI が出てしまう。

**確認**:

- 非公開作品の PDF を、クッキーを付けずに `/uploads/<ファイル名>` で取得できた（200、約 465KB）。
  同じ作品のビューア画面は 403 だった。
- 未ログインのまま Socket.io で非公開作品（id=4）の部屋に入り、コメントを送信できた。
  そのコメントは `chat_messages` テーブルに保存された。

認証を画面にかけてリソースにかけていない、という典型的な欠陥である。

### 3. ページネーション後にフィルタしている

`/`、`/comics`、`/searchform` は `LIMIT / OFFSET` で取得したあとに配列を filter しているため、
表示件数が不足し、次ページの起点もずれる。絞り込み条件は SQL 側に置くべきだった。
（`/search` はそもそもページネーションがなく、全件取得している。）

### 4. 白紙ページの挿入が、非冪等なうえに1回でも壊れる

`addBlankPageToPdf()` は `addPage()` で末尾に白紙を追加したあと、
**同じページオブジェクトを `insertPage(0, ...)` で先頭にも挿入している。**
pdf-lib の `insertPage` は既存ページの重複を取り除かないため、
1回の実行で白紙が先頭と末尾の2か所に入る。

さらに `removeBlankPageFromPdf()` は先頭しか削除しないので、
追加→削除を行うと末尾の白紙だけが残る。

加えて、実行前に現在の状態を確認していないため二重実行でさらに増え、
`fs.renameSync(tempPdfPath, pdfPath)` で元 PDF を上書きしているため復元もできない。

**確認**（9ページのダミー PDF で実行）:

| 操作 | ページ数 |
|---|---|
| アップロード直後（奇数だったので末尾に1枚追加された） | 10 |
| `add` 1回 | **12**（+2） |
| `add` もう1回 | 14 |
| `remove` 1回 | 13（先頭の1枚しか消えない） |

原本を保持したまま状態をフラグで管理し、表示時に派生物を作る設計にすべきだった。

### 5. パス表現が統一されていない

サムネイルは multer の相対パス（`uploads/...`）、PDF は `path.join()` による絶対パスで
DB に保存されている（**確認**: 同じ1件の作品が `uploads/1789...png` と
`C:\...\MIMO\uploads\resized-1789...pdf` という別形式で入る）。そのためコード全体に `path.basename()` が散在している
（`app.js` 内に10か所以上）。保存時に形式を正規化していれば不要だった。

### 6. リサイズ前の原本 PDF が残り続ける

アップロードされた PDF は `resized-` を付けた別ファイルにリサイズ保存され、
DB にはそちらのパスだけが入る。元のファイルは参照されないままディスクに残り、
`/delete-comic` も DB に記録されたパスしか消さないため、削除もされない。

**確認**: 5件アップロードしたところ、`uploads/` には元ファイル5個とリサイズ後5個の
合計10個が残った。

### 7. 教員アカウントの登録が URL の秘匿だけで守られている

教員登録フォームは `/dontshare` という公開ルートで、知っていれば誰でも
role=2（教員）のアカウントを作成できる。教員限定公開の作品はこの role で判定しているため、
公開範囲の設計がこの一点に依存してしまっていた。

### 8. 状態を変更する POST に CSRF 対策がない

認証を httpOnly クッキーだけで行っており、`/submit`、`/delete-comic`、
`/update-comic-role` などにトークン検証がない。

### 9. その他

- 認証結果やアクセス判定の内容を `console.log` でそのまま出力している（ユーザー情報を含む）。
- `package.json` に実際には使っていない依存が残っている（`body-parser`、`canvas`、`ejs-lint`、`mysql`、`pdfjs-dist`）。特に `canvas` はネイティブビルドが必要で、インストールを重くしていた。
- `canAccessComic()` の `role === 4`（非公開）の分岐は、先頭の所有者チェックで必ず処理されるため到達しない。
- DB のスキーマ定義がリポジトリに入っていない。動かすには手元で作り直す必要がある（`docs/schema-reconstructed.sql` は今回復元したもの）。
